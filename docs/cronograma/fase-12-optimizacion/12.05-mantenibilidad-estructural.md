## Objetivo y límites

Reducir el conjunto de archivos y conocimiento ajeno necesario para modificar una feature:
dominio, aplicación, puertos, adaptadores pertinentes y UI. Optimizar el radio de contexto,
no LOC, cantidad de archivos o apariencia de modularidad. Una extracción debe reducir
superficie no relacionada sin aumentar significativamente los saltos de navegación.

Se conserva composición TypeScript explícita, exports públicos, comportamiento observable,
contratos HTTP/eventos, ownership y límites transaccionales. No se introducen contenedores DI,
service locators, reflection, registro mágico, repositorios universales, clases base genéricas,
interfaces sin consumidor ni wrappers de una línea sin frontera semántica. No se crean
microarchivos, barrels globales nuevos ni cajones `utils`/`shared`. La pequeña duplicación no
justifica una abstracción. No se agregan dependencias para este trabajo.

Gobiernan [capas](../../architecture/01-capas.md),
[módulos](../../architecture/02-modulos.md), ADR-0001, ADR-0002, ADR-0003 y ADR-0009.
Para composición de venta y LAN se añaden ADR-0026 y el escenario
[FS-005](../../failure-scenarios/FS-005-venta-concurrente-ultima-unidad.md).
Una reubicación que conserva estas decisiones no necesita un ADR nuevo. Si exige cambiar
autoridad, atomicidad, fallos o contratos, se detiene ese corte y se decide normativamente
antes de implementarlo; no se modifica una especificación para hacer pasar tests.

- [x] Mantener un ensamblador explícito y parámetros concretos; no pasar todo el runtime a

- [x] Mantener `createSecurityRuntime`, `SecurityRuntime` y `ADMIN_PERMISSIONS` para los
  consumidores actuales; evitar renombrado masivo de entrada. Ninguno cambió de nombre ni de
  archivo.
- [x] Revisar también `app.ts`: `ServerDependencies` y helpers HTTP son consumidos por rutas.
  Separar el contrato/helpers del registrador solo si evita cargar el hub al editar una ruta;
  no hacer que los módulos importen la implementación del runtime para obtener sus tipos.
  Separados: el contrato en `server-dependencies.ts` y los helpers en `http-context.ts`, que
  toma el tipo del contrato y no del runtime.

**Lo medido.** Editar una ruta abría `app.ts` entero, 445 líneas con el contrato, los helpers y
el arranque de Fastify. Ahora una ruta importa 180 líneas de contrato y 118 de contexto HTTP, y
no toca el registrador, que queda en 179. **Ninguna ruta de producción importa ya `app.ts`**, así
que la dependencia de ida y vuelta que el diagnóstico registró desaparece sin una regla que la
prohíba. Agregar un reporte abre 44 líneas en vez de buscar su cableado entre 752.

**Por qué no se extendió el patrón.** El plan pide comparar antes de extender, y la comparación
es clara: reportes necesitaba **dos** piezas, y el salto al siguiente candidato es grande. Los
grupos restantes usan entre siete y veintidós piezas —repositorios, reloj, generadores, unidad de
trabajo, almacén de eventos, auditoría, idempotencia, outbox— y extraerlos significaría una firma
de diez parámetros o una bolsa con el runtime dentro, que es justo lo que este corte tiene
prohibido. La composición entre contextos es trabajo del root y se queda ahí.

Aceptación: una dependencia local se conecta en su composición local; el root declara las
relaciones entre módulos. Se preservan el emisor fiscal compartido, consentimiento X/Z,

No se instancian dos DB, impresoras o workers. Verificar contratos HTTP, venta real y E2E LAN.

## 12.05.07 — Architectural boundary protection

**Entregada el 2026-09-17** en `a926f32`.

- [x] Extender ESLint y `tests/eslint-boundaries.test.ts`, sin herramientas adicionales.
  Cuatro bloques nuevos de `no-restricted-imports` y quince fixtures; ninguna dependencia nueva.
- [x] Añadir fixtures negativos y positivos: renderer → DB/core/Node; domain → application,
  apps/drivers; application → adaptadores; imports internos entre paquetes.
  Nueve negativos y **seis positivos**: una regla que sólo prohíbe no demuestra que deja trabajar.
- [x] Proteger nuevos módulos de imports de implementación hacia el composition root.
  Ni las rutas, ni el contrato, ni los helpers HTTP, ni las composiciones locales alcanzan
  `runtime.ts`; un grupo de operaciones del cliente no importa el ensamblador que lo reúne.
- [x] Cubrir formas de importación relativas, aliases públicos y reexports relevantes; las
  reglas de patrones actuales no prueban por sí solas todos esos caminos.
  Los grupos cubren la forma relativa y la global —`../app.ts` y `**/app.ts`— y ambas extensiones,
  porque el servidor importa con `.ts` y el renderer con `.js`.
- [x] Para cruces de contexto, proteger el puerto concreto acordado, sin prohibir los cruces
  legítimos sales → cash/inventory ni inventar una independencia absoluta.
  **No se agregó ninguna regla entre contextos de negocio.** Los cruces de venta con caja e
  inventario son la coordinación que ADR-0026 acordó, y los archivos de persistencia separados en
  12.05.03 no introdujeron una frontera nueva: siguen detrás del mismo export público.

**Las cuatro fronteras protegidas.** Una ruta usa el contrato y los helpers HTTP, no el
registrador ni el runtime —es la dependencia de ida y vuelta que el diagnóstico registró—. El
contrato, los helpers y las composiciones locales no alcanzan el runtime, que se inyecta. Un
grupo de operaciones del cliente no importa el ensamblador, que sería el ciclo equivalente en el
renderer. Y la navegación no depende del shell, porque es lógica pura.

Las rutas excluyen sus propias pruebas de contrato, que construyen la app y por eso sí importan
el registrador. El lint global no encontró un solo falso positivo sobre el código real.

Aceptación: cada frontera nueva falla con una violación representativa y acepta su uso válido.
Las pruebas existentes de renderer son seis probes; no se presentan como análisis completo
del grafo. Incorporar protección junto al corte que introduce la frontera, no solo al final.

## Orden, validación y commits

Primero refrescar la baseline/documentación y reconocer las instrucciones existentes. Tras el gate,
priorizar persistencia (menor riesgo observado), composición, cliente HTTP y cortes UI justificados;
acompañar cada frontera con tests. Terminar con benchmark. La numeración no obliga a extraer
runtime antes de DB y 12.04 suspendida no impide 12.05. Ejecutarla después de 12.03 evita que la
separación física de repositorios invalide las mediciones SQLite o se mezcle con una optimización
de consultas.

Hitos previstos, cada uno condicionado a evidencia y checks verdes:

1. `docs(architecture): plan context radius optimization` — diagnóstico, baseline y cronograma.
2. `refactor(db): localize repository implementations` — clases base, exports y consumidores.
3. `refactor(server): localize runtime composition` — separar primero un grupo verificable;
   repetir por capacidad si el resto exige cortes independientes.
4. `refactor(desktop): group API operations by feature` — transporte y grupos con sus consumidores.
5. `refactor(desktop): isolate navigation from application shell` — solo si el ensayo lo justifica.
6. `refactor(desktop): isolate purchase receipt workflow` — solo con interacción preservada.
7. `test(architecture): protect module composition boundaries` — únicamente cobertura transversal
   restante; las fronteras de cada extracción se validan en su propio hito.
8. `docs(architecture): record context radius comparison` — evidencia final, no ahorro supuesto.

Antes de cada commit: status, diff, lint, typecheck, tests pertinentes y boundaries; stage con
rutas explícitas y revisión de `git diff --cached`. No commitear fallos conocidos ni trabajo ajeno.
Para código ejecutar además el mínimo global `pnpm lint`, `pnpm typecheck`, `pnpm test`;
infraestructura transversal exige suites de integración/E2E relevantes. Para documentación,
lint, typecheck solicitado y pruebas arquitectónicas existentes, rutas y `git diff --check`;
no ejecutar suites funcionales costosas sin cambio funcional. Registrar resultados al cerrar
el hito. No modificar semántica de negocio dentro de un refactor estructural.

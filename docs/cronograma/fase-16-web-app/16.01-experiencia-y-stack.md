# Sub-fase 16.01: Experiencia de usuario y selección del stack

- **Fase:** [16 — Web App interna con Next.js](./README.md).
- **Estado:** Pendiente; fuera del MVP.
- **Dependencia:** Fase 15 cerrada; identidad y permisos cloud de Fase 14 disponibles.

## Objetivo

Explorar soluciones de interfaz y dejar una base técnica fundada para la web.

## Tareas

- [ ] Definir recorridos de búsqueda, comparación por almacén, detalle por lote y lectura de kardex con personal interno.
- [ ] Explorar propuestas visuales de listado denso, detalle y móvil; validar jerarquía, navegación, legibilidad y estados de sincronización.
- [ ] Adoptar Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui y TanStack Query; identificar los casos de estado UI que requieren Zustand.
- [ ] Evaluar bibliotecas complementarias mediante los criterios y fuentes del estudio incluido abajo; fijar versiones compatibles al implementar.
- [ ] Crear la base de apps/web cuando corresponda, con límites de imports y dependencias respecto a core, drivers y desktop.
- [ ] Definir navegadores, dispositivos, accesibilidad y presupuestos de carga/interacción medibles; registrar la decisión UX y técnica.

## Criterios de aceptación

- Existe un recorrido validado en escritorio y móvil y una selección de dependencias justificada.
- Las fronteras Next.js/Fastify y servidor/cliente son explícitas y no exponen base de datos al frontend.
- La elección no aplica Ponytail ni reduce calidad visual/accesibilidad para minimizar dependencias.

## Exploración inicial de tecnologías

Consulta de fuentes oficiales: **2026-09-06**. Esta selección fundamenta la planificación;
no es un benchmark ni demuestra una interfaz implementada. Las versiones concretas y
dependencias transitivas se revisan al ejecutar 16.01.

**Ponytail NO aplica en 16 ni 16B.** Se evalúa calidad de la experiencia, no solo tamaño del
código. La elección de Next.js, Tailwind, shadcn/ui y TanStack Query ya está aceptada en
[ADR-0025](../../architecture/adr/0025-web-nextjs-y-sistema-de-diseno.md).
Zustand está autorizado para los casos de estado compartido UI que se identifiquen.

| Tecnología | Uso previsto o candidato | Evaluación pendiente |
|---|---|---|
| Next.js App Router | Framework web aprobado; layouts y composición servidor/cliente | Límites de renderizado, build de producción, sesión y despliegue compatible |
| Tailwind CSS | Estilos y tokens aprobados | Densidad, responsive y conexión con tokens semánticos propios de 16B |
| shadcn/ui | Base aprobada para componentes editables | Seleccionar familia de primitivas compatible, personalizar interacciones y comprobar teclado/SSR |
| TanStack Query | Estado remoto aprobado | Claves, hidratación, aislamiento por usuario y revalidación sin falsear frescura del inventario |
| Zustand | Autorizado para estado UI compartido necesario | Preferencias/paneles; evitar duplicar URL, consultas remotas o credenciales |
| TanStack Table | Candidato recomendado para listado de inventario | Columnas, orden/filtros/paginación controlados por servidor y navegación accesible |
| Storybook con integración Next.js/Vite | Candidato recomendado para documentación de 16B | Compatibilidad de componentes, mocks de contexto, ejemplos y pruebas visuales |
| Playwright | Candidato recomendado para recorridos completos y capturas | Navegadores acordados, sesión, estados de red, responsive y repetibilidad |
| axe-core e integración con las pruebas elegidas | Candidato para detectar problemas de accesibilidad | Cobertura automática más revisión manual de teclado, foco y lectura |

TanStack Table gestiona el comportamiento tabular y shadcn/ui la presentación; se evaluará
esa combinación para consultas densas. La virtualización, una biblioteca de formularios,
iconografía o animación pueden incorporarse cuando el recorrido o las mediciones lo
justifiquen. No quedan prohibidas por no figurar en esta lista, ni se agregan como paquetes
sin un caso de uso verificable.

No se escogerá una biblioteca UI completa incompatible con la base shadcn sin documentar
por qué mejora una necesidad concreta. La familia exacta de primitivas y su compatibilidad
con las versiones seleccionadas se comprueban con los componentes reales, no por popularidad.

## Método de selección durante la fase

1. Prototipar listado de inventario, filtros, detalle y estado desactualizado en escritorio y móvil.
2. Comparar legibilidad, uso con teclado, foco, densidad, esfuerzo de personalización y soporte SSR.
3. Medir carga e interacción con el volumen de datos acordado; distinguir coste de red/API de renderizado.
4. Registrar dependencia, versión, necesidad, alternativa evaluada, licencia, mantenimiento y resultado.
5. Validar el recorrido con producto y fijar una combinación coherente para que 16B la convierta
   en el sistema de diseño propio.
